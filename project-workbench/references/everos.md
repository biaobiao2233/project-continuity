# EverOS / Derived Memory Usage

Use EverOS only when its memory tools are actually available in the current session.

Treat it as read-mostly semantic/historical memory and an index across agent sessions. It is useful for discovery; it is not the authoritative current project ledger.

## Evidence level

EverOS output is derived memory/index evidence. Never use it alone to prove:

- current live machine/repo state;
- exact current user authorization;
- final acceptance/PASS;
- exact wording when a source conversation/file is available;
- current production state.

If it conflicts with Project Continuity, current repo/files or live evidence, return to the higher-authority source.

## Typical workflow

```text
Project Spine / Active Work Node
→ relevant Closure/source pointers
→ EverOS semantic search if history is missing
→ exact source/session/artifact when needed
→ current repo/live verification
```

Use derived memory to reduce rediscovery, not to bypass verification.

## Write boundary

Do not automatically push every runtime event or Handoff into EverOS.

Good long-term candidates include durable requirements, accepted closures, major discoveries/pitfalls and stable source pointers. Memory writes still require the user's/runtime's normal authorization path.
